# تعليمات تسليم إلى الذكاء الاصطناعي داخل Visual Studio Code
أنت مسؤول عن الطرف المُرسل فقط. لا تُعد تصميم النظام الخارجي ولا تنشئ محرك رسائل موازياً. اقرأ هذا العقد وREADME والتقرير قبل تعديل أي ملفات. طبّق التغيير على فرع منفصل واحتفظ بإمكانية الرجوع. لا تعتمد على اسم نموذجك لإثبات صحة الكود، بل على نتائج الاختبارات.

## الحدود الملزمة
1. افحص المشروع محليًا لتحدد موضع المعالجة الخلفية الآمنة. لا تفترض إطار عمل أو مزوّد استضافة. إن لم توجد بيئة خادم تحفظ الأسرار، وضّح الفجوة واقترح أقل إضافة خادمية متوافقة ثم اطلب اعتمادها. لا تضع المفتاح في المتصفح كحل بديل.
2. لا ترسل مباشرة إلى Sheets. أرسل من خادم موثوق إلى Apps Script /exec. لا تستخدم no-cors ولا تتعامل مع استجابة opaque كنجاح. لا تستخدم JSONP للبيانات الشخصية.
3. احتفظ بسر INGEST في متغير بيئة خادمي غير عام. سر ADMIN يبقى لدى مسؤول النظام الخارجي وليس ضمن استقبال الزوار. لا NEXT_PUBLIC_ أو VITE_ أو مشابه للأسرار. لا تطبع أي سر في السجلات.
4. لا تسمح للطرف غير الموثوق باختيار event.type كيف يشاء. مسار الإدخال يسمح request.create وrequest.complete فقط. أي request.get يجب أن تتحقق قبله من امتلاك الجلسة للطلب؛ معرفة request_id ليست إذنًا. لا تمرر طلبات تأكيد أو إلغاء إدارية إلى الخادم بتوقيع INGEST.
5. ضع حماية إساءة محلية عند حافة الخادم: تحقق من المصدر المسموح، وحد الطلبات، وحجم الجسم، وربط الطلب بالجلسة، وCSRF حين تستخدم جلسات cookies. لا تنشئ POST مفتوحًا يحوّل أي جسم إلى طلب موقع بتوقيعك. لا يُعَد Origin وحده مصادقة.
6. هذه نسخة وهمية فقط، والفرع الوحيد DEMO_BRANCH، والعناوين محصورة في ALLOWED_EMAILS. لا تجمع هاتفًا ولا معلومات طبية ولا اسم مريض حقيقي. لا ترسل البيانات إلى تحليلات أو خدمات ذكاء اصطناعي.

## عقد الحدث v1
جسم الحدث JSON يحتوي بالضبط type, request_id, data. المرجع يُعاد بعد الحفظ. request_id معرف عشوائي ثابت لمحاولة الحجز المنطقية (مثل demo-UUID)، وevent_id معرف عشوائي ثابت لذلك الحدث. لا تغيّر أيًّا منهما ولا نص body عند إعادة المحاولة. حدث جديد مثل استكمال البيانات له event_id جديد ونفس request_id.
request.create: data = is_test:true, name (1-60), email (عنوان مسموح), phase:SUBMITTED أو INCOMPLETE, consent، وbranch_id وpreferred_at فقط عند SUBMITTED.
consent = service:true, followup:boolean, review:boolean, at:ISO-with-offset, version:demo-email-v1, source:demo-form. املأ الموافقات من قرار صريح، لا قيمة افتراضية مخفية. INCOMPLETE يتطلب followup:true وإرسالًا صريحًا لطلب المساعدة. service:false يعني عدم إرسال الحدث التجريبي، وليس التحايل بقلبه إلى true.
request.complete: data = expected_version, branch_id:DEMO_BRANCH, preferred_at. مسموح فقط من INCOMPLETE. لا تُعد إرسال بيانات التواصل لتغييرها.
request.get: data={} ويُستخدم بعد تحقق جلسة الطرف الطالب. لا تعِد للمستخدم بيانات غير لازمة.
التواريخ بصيغة ISO كاملة، مثل 2026-09-09T12:00:00+03:00. ولّد أوقاتًا مستقبلية وقت التنفيذ؛ أمثلة التاريخ ليست مواعيد ثابتة للعرض.

## توقيع النقل
env = {v:1,key_id:"ingest",ts:Unix seconds,event_id,body:EXACT_JSON_STRING,signature:LOWERCASE_HEX}
message = String(v)+"\n"+key_id+"\n"+String(ts)+"\n"+event_id+"\n"+body
signature = HMAC-SHA256(message UTF-8, INGEST_SECRET UTF-8), lowercase hex, 64 characters.
المفتاح نص URL-safe عشوائي؛ لا تفك base64 له قبل التوقيع. لا يوجد سطر إضافي بعد body إلا إذا كان جزءًا فعليًا منه. يُرسل envelope نفسه كـ JSON إلى /exec، وليس body وحده. التوقيع في الجسم لأن معالج Apps Script لا يوفّر هنا واجهة موثقة لقراءة Authorization أو arbitrary headers.
التوقيع صالح ±300 ثانية. في كل إعادة محاولة حدّث ts وsignature فقط مع الإبقاء على body وevent_id كما هما. اتبع تحويل Google إلى script.googleusercontent.com ولا تفرض إعادة POST على تحويل 302. لا تسرب السر إلى URL.

## تفسير النتيجة
HTTP 200 وحده ليس نجاحًا. يلزم JSON صحيح وok:true وdata.request_id مطابق. عند duplicate:true فهذا قبول سابق وليس طلبًا جديدًا. data.status هي الحالة الحالية وقد تتغير بعد القبول الأول، وevent_version هو إصدار الحدث الذي قُبل أول مرة.
لا تعرض «تم تأكيد الموعد» بعد request.create. النص الصحيح: «استلمنا طلبك، بانتظار مراجعة الاستقبال».
عند BUSY أو INTERNAL_RETRY_SAME_EVENT أو انقطاع الشبكة: احتفظ بنفس الحدث وأعد المحاولة بحد أقصى 3 مرات، فواصل 2 ثم 4 ثوانٍ؛ إن لم يتأكد القبول فاعرض «لم نتأكد من التسجيل بعد» مع مسار إعادة المحاولة نفسه، لا نجاحًا وهميًا ولا فشلًا قطعيًا.
عند VERSION_CONFLICT اقرأ الحالة المصرح بها واطلب قرارًا جديدًا إن لزم؛ لا تتجاوز التعارض تلقائيًا. عند REQUEST_EXISTS اقرأ نفس الطلب بدل إنشاء آخر. عند IDEMPOTENCY_CONFLICT أوقف المسار وافحص تغيّر الجسم أو إعادة استخدام المعرف. لا تعِد توليد المعرفات لعلاج الأخطاء.

## ما يجب أن تسلّمه بعد التنفيذ
ملخص الملفات المعدلة دون إعادة بناء واسعة، ومتغيرات البيئة المطلوبة دون قيم، واختبارات ناجحة لربط الحدث، وتحميل مزدوج، وفقد الاستجابة بعد الحفظ، وانتهاء التوقيع، وانقطاع الشبكة، وعدم وجود الأسرار في الحزمة العامة. أرفق مرجع طلب واحد ظاهرًا في Requests ومطابقًا للاستجابة. لا تقل إن البريد وصل إلا بعد فحص صندوق الاختبار، ولا تقل إنك اختبرت كود Apps Script على Google إذا اختبرت محاكاة محلية فقط.
قبل أي تغيير لعقد v1، قدّم اقتراحًا وتحديث اختبارات للطرفين. لا تضف Calendar أو WhatsApp أو قاعدة بيانات أخرى إلى مسار عرض الغد من تلقاء نفسك.
