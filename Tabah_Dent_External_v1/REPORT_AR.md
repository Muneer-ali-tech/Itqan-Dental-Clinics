## 1. القرار التنفيذي الذي أنصح بتنفيذه الليلة
ابنِ مسارًا واحدًا مترابطًا، لا مجموعة عروض منفصلة: حدث طلب تجريبي موقّع، ثم تحقق، ثم سجل موثوق، ثم قائمة رسائل تنتظر التنفيذ، ثم إرسال بريد اختباري، ثم تغيير حالة الطلب، ثم إثبات توقف الرسائل التابعة له. Google Apps Script يستقبل البيانات أولًا، ويكتب في Google Sheets بعد التحقق. لا نعكس الترتيب بفتح الجدول للكتابة العامة.
البريد هو قناة الإرسال الفعلية في هذه النسخة. لا تحتاج رقم WhatsApp أو مزوّدًا مدفوعًا لإثبات منطق الحالات. النقل إلى WhatsApp مستقبلًا يُبقي قواعد الطلب والأهلية والإلغاء، ويضيف محوّل قناة وموافقات وأحداث تسليم؛ ليس استبدال اسم حقل email بكلمة phone.
«نظام متكامل» هنا يعني اكتمال مسار العرض المحدد، وليس اكتمال أنظمة العيادة أو جدولة الأطباء أو سجل المرضى. لا توجد وظيفة توليدية داخل مسار التنفيذ؛ نصوص الرسائل ثابتة، والتحقق حتمي، وقرارات التأكيد بيد مسؤول التجربة. هذا يقلل التباين ومخاطر العرض.
الأولوية: الحفظ الصحيح، منع التكرار، التمييز بين الطلب والتأكيد، ثم منع الإرسال بعد الإلغاء. التقييم التجريبي واستكمال الطلب الناقص اختبارات إضافية بعد نجاح الأولويات، لا سبب لتعطيلها.

## 2. ما بُني بالفعل، وما لم يُثبت بعد
أُنتجت ستة ملفات Apps Script تنفيذية وملف الصلاحيات، وأداة Python لاختبار نقطة الاستقبال، ومولّد أحداث وهمية، وحزمة اختبارات Node.js، وتعليمات مستقلة للطرف المرسل. جميع ملفات التشغيل كاملة في الملحق وفي الحزمة المضغوطة، وليست شيفرة تقريبية أو دوال تُترك لك لتكملها.
شُغّلت 59 حالة اختبار محلية على ملفات .gs نفسها، مع محاكاة Google Sheets والأقفال والساعة والإرسال؛ نجحت 59 من 59. شُغّل أيضًا فحص تطابق توقيع HMAC لنص عربي بين Python وNode، وفحص بنية أدوات Python وتشغيل إنشاء أمثلة والتحقق منها دون شبكة.
لم يُنشر المشروع داخل حسابك، ولم يُنشأ جدول لك، ولم يُرسل بريد، ولم تُختبر صلاحيات Google أو نقطة /exec أو وصول رسالة حقيقية إلى البريد. بيئة الاختبار المحلية هنا لا تملك اتصالًا بالإنترنت؛ لذا لا تستطيع اختبار النشر الفعلي. تمت مراجعة التوثيق الرسمي بواسطة بحث منفصل. هذا فرق أساسي بين صحة المنطق محليًا وصحة الربط الفعلي.
لا يمكنني التصديق بأن النظام «مثالي» أو خالٍ من جميع الأخطاء. الدليل العملي المقبول: نجاح اختبارات القبول الحية الواردة لاحقًا داخل حسابك، وتسجيل النتيجة والتوقيت والمرجع. لا تستبدل ذلك بعبارة «الكود مكتوب إذن يعمل».
لم أعد استخدام الاستنتاجات التجارية والأسعار من التقرير السابق؛ ما أُخذ منه هو نطاق التجربة، والحالات، وضوابط التوقف، والفصل بين طلب الموعد والتأكيد، وتأجيل الأنظمة غير المعروفة.

## 4. الخريطة المعتمدة وتوزيع المسؤوليات
المسار التنفيذي بالترتيب: مُرسل خادمي موثوق → HTTPS POST موقّع → doPost → فحص التوقيع والوقت والصلاحية والحقول → قفل مشترك → تحميل الحالة ومنع التكرار → انتقال حالة صحيح → حفظ الحالة والحدث والمهام معًا → إرجاع JSON بالمرجع → مشغّل زمني → إعادة فحص الأهلية → البريد → تحديث سجل الإرسال.
Google Sheets هو مخزن الاختبار وواجهة المتابعة الإدارية. State هو السجل المرجعي. تبويبات Requests وOutbox وAudit وOps وDashboard نسخ عرض مشتقة منه، وليست مصادر تعديل الحالة. قد تتأخر حتى التشغيل التالي أو زر تحديث الجداول. قبول الحدث لا ينتظر تحديثها، لتجنب الخلط بين فشل عرض الجدول وفشل حفظ الطلب.
أنا سلّمت منطق النظام الخارجي وأكواد التحقق والجدولة والإرسال والتشغيل. الذكاء الاصطناعي داخل Visual Studio Code مسؤول عن تنفيذ المُرسل المتوافق مع العقد، وحماية أسراره، وربط نتائج الطلب بالطرف المستخدم، واختبار عقد الربط من جهته. أنت مسؤول عن حساب Google والإعدادات والنشر وعناوين الاختبار وقبول النتائج. مسؤول التجربة يحاكي الاستقبال ويعتمد الحالة، ولا يوجد قرار طبي آلي.
لا تضع Google Sheets API بين الطرف المرسل وهذه الآلية. كتابة API أو شيفرة في خلية لا تُشغّل onEdit تلقائيًا بحسب توثيق Google. ولهذا لا يعتمد التنفيذ على onEdit أصلًا. من يريد إدخال حالة يُرسل حدثًا أو يستخدم قائمة Tabah DEMO.
إذا لم توجد لدى الطرف المرسل بيئة خادم آمنة، فذلك متطلب تكامل على الجهة المسؤولة عنه، وليس إذنًا بوضع مفاتيح التوقيع في JavaScript العام. لا تفترض وجودها، ولا تغيّر تقنيته من هذا التقرير.

## 6. عقد البيانات: معرّف الطلب ليس معرّف الحدث
request_id ثابت للطلب المنطقي من البداية للنهاية. يجب أن يكون عشوائيًا غير متسلسل، مثل demo- ثم UUID. event_id ثابت للحدث الواحد عند إعادة محاولته، ويتغير فقط عند حدوث عملية جديدة. نفس request_id يمكن أن يتلقى إنشاء، ثم مراجعة، ثم تأكيدًا، ثم إلغاء؛ لكل عملية event_id مستقل.
يتحقق الكود من طول المعرّفات وحروفها، لكنه لا يستطيع إثبات عشوائيتها؛ يجب أن يولدها المُرسل توليدًا مناسبًا. مرجع TD- مشتق من request_id، ولا يُستخدم ككلمة مرور أو تصريح لتعديل الطلب.
| الحقل | القاعدة | سببها |
| type | اسم حدث معروف فقط | منع تنفيذ عمليات غير مقصودة |
| request_id | 8 إلى 80 حرفًا من الأحرف والأرقام والشرطة والشرطة السفلية؛ يبدأ بحرف أو رقم | ثبات التتبع ومنع الحقول الحرة |
| data.is_test | القيمة المنطقية true فقط عند الإنشاء | لا إدخال إنتاجي عن طريق الخطأ |
| data.name | اسم اختبار بطول 1 إلى 60 دون محارف تحكم | تقليل البيانات وتجنب حقن السجل |
| data.email | عنوان واحد، بحد 120، داخل قائمة الاختبار | لا إرسال للمرضى أو لعناوين عشوائية |
| data.phase | SUBMITTED أو INCOMPLETE | التمييز بين طلب كامل وطلب مساعدة |
| branch_id | DEMO_BRANCH فقط في الطلب المكتمل | لا افتراض لفروع حقيقية |
| preferred_at | وقت ISO مستقبلي، أقل من 90 يومًا | رغبة في الموعد وليست حجزًا |
| consent.service | true صريحة | شرط هذه التجربة للمراسلة الخدمية |
| consent.followup | boolean، ويجب true للطلب الناقص | عدم استرداد اهتمام بلا إذن |
| consent.review | boolean مستقلة | عدم فرض طلب التقييم |
| consent.at | ISO بمنطقة زمنية، ليس أقدم من 24 ساعة ولا يتقدم أكثر من 5 دقائق | قيد خاص بتجربة الموافقة الجديدة |
| consent.version وsource | demo-email-v1 وdemo-form | توثيق نسخة النص ومصدر الإجراء |
| expected_version | عدد صحيح يطابق version الحالي عند التعديل | منع الكتابة اعتمادًا على حالة قديمة |
لا تُقبل حقول تشخيص أو ملاحظات طبية أو أرقام هوية أو هاتف أو حقول إضافية غير موثقة. القيم النصية "true" ليست بديلًا عن true المنطقية. لا يُعد is_test:true ضمانًا أن البيانات وهمية؛ أنت والطرف المرسل مسؤولان عن عدم إدخال أشخاص حقيقيين.
البريد الثابت غير قابل للتعديل عبر أحداث هذه النسخة. إذا أخطأت بعنوان الاختبار، أغلق الطلب وأنشئ حالة اختبار جديدة بعد تصحيح الإعدادات. لا تعدّل State يدويًا.

## 7. أمثلة دقيقة لأجسام الأحداث
الأمثلة التالية للتوضيح. أعد توليد consent.at والأوقات المستقبلية بواسطة make_examples.py عند التنفيذ؛ التواريخ الثابتة قد تصبح قديمة. لا ترسل العنوان example.com إلا في المحاكاة؛ للإرسال الحي استعمل بريد اختبار تملكه وأضفه للقائمة.
```json
{
  "type": "request.create",
  "request_id": "demo-9c6cc4b8-2c00-4b6c-90e8-22eef085827f",
  "data": {
    "is_test": true,
    "name": "زائر وهمي للاختبار",
    "email": "demo@example.com",
    "phase": "SUBMITTED",
    "branch_id": "DEMO_BRANCH",
    "preferred_at": "2026-09-09T12:00:00+03:00",
    "consent": {
      "service": true,
      "followup": true,
      "review": false,
      "at": "2026-09-07T10:00:00+03:00",
      "version": "demo-email-v1",
      "source": "demo-form"
    }
  }
}
```
الطلب الناقص يستخدم phase:INCOMPLETE، ويحذف branch_id وpreferred_at بالكامل، ويحتفظ بوسيلة التواصل وموافقة المتابعة. لا تُرسل null لهذين الحقلين؛ يُحذفان. هذا حدث إرسال صريح من صاحب التجربة، وليس قراءة تلقائية للبيانات قبل الإرسال.
استكمال الطلب يتم بمفتاح ingest على نفس request_id، وبعد قراءة الإصدار الصحيح:
```json
{
  "type": "request.complete",
  "request_id": "demo-9c6cc4b8-2c00-4b6c-90e8-22eef085827f",
  "data": {
    "expected_version": 1,
    "branch_id": "DEMO_BRANCH",
    "preferred_at": "2026-09-09T12:00:00+03:00"
  }
}
```
المثال الإداري التالي يرسل بمفتاح admin فقط. غيّر expected_version إذا مر الطلب بالمراجعة أو بأي تعديل سابق:
```json
{
  "type": "request.confirm",
  "request_id": "demo-9c6cc4b8-2c00-4b6c-90e8-22eef085827f",
  "data": {
    "expected_version": 1,
    "appointment_at": "2026-09-09T12:00:00+03:00"
  }
}
```
النجاح النموذجي لا يحتوي الاسم أو البريد:
```json
{
  "ok": true,
  "duplicate": false,
  "event_version": 1,
  "data": {
    "request_id": "demo-9c6cc4b8-2c00-4b6c-90e8-22eef085827f",
    "reference": "TD-demo-9c6cc4b8-2c00-4b6c-90e8-22eef085827f",
    "status": "SUBMITTED",
    "version": 1,
    "is_test": true,
    "appointment_at": null,
    "contact_stopped": false
  }
}
```
إذا كان contact.stop محفوظًا في قائمة الحظر العامة ولكن تعطل تحديث الطلب، قد تظهر contact_stopped:false في طلب آخر للبريد نفسه. قرار الإرسال يفحص Suppression أيضًا ولا يعتمد على هذا الحقل وحده. لا تعرضه كحكم شامل على كل الطلبات المرتبطة بعنوان واحد.

## 8. التوقيع والصلاحيات وحماية النقل
نقطة /exec ليست سرًا. يمكن فتح doGet علنًا لكنه يعيد حالة LIVENESS_ONLY بلا أسماء أو جدول أو إعدادات. سلامة doGet لا تثبت أن الكتابة أو الإرسال أو المشغّل يعمل.
الصلاحية تنقسم إلى مفتاح ingest للإنشاء والاستكمال والقراءة المقيدة، ومفتاح admin لعمليات الاستقبال. مفتاح ingest لا يؤكد ولا يلغي ولا يسجل الحضور. التطبيق المنشور يعمل بصلاحيات مالكه، لذا لا يصح الاعتماد على Session لتحديد هوية الزائر، ولا على قيمة actor يضعها المرسل. دور الحدث يأتي من المفتاح الذي جرى التحقق منه.
هذا ليس نظام مستخدمين متعدد الأدوار. كل مالك لمفتاح admin يمتلك صلاحيات مسؤول التجربة، وكل محرر للمشروع قد يستطيع قراءة الأسرار. لا تشارك الملف بصلاحية تحرير مع زوار العرض. في الإنتاج يلزم تحقق مستخدمين منفصل وصلاحيات وإسناد دقيق للمسؤول، لا مفتاح مشترك فقط.
يُوقّع نص يتكون من v ثم key_id ثم ts ثم event_id ثم body، يفصل بينها محرف newline واحد. body نص JSON كما أُنشئ، لا كائن يعاد ترتيبه بعد التوقيع. ثم يوضع التوقيع بصيغة hex صغيرة في ظرف النقل. أدوات الاختبار المرفقة تنفذ ذلك كاملًا.
```text
String(v) + "\n" + key_id + "\n" + String(ts)
+ "\n" + event_id + "\n" + body
```
التوقيع صالح ضمن خمس دقائق من وقت الخادم في الاتجاهين. إعادة إرسال الحدث داخل النافذة لا تُكرره بسبب سجل الأحداث. بعد انقضاء النافذة، أعد التوقيع بوقت جديد مع المحافظة على body وevent_id. لا تستخدم معرفًا جديدًا بسبب timeout.
تُرفض إعادة استخدام event_id مع body مختلف حتى لو لم يتغير المعنى الظاهري؛ تغيير المسافات أو ترتيب الحقول أو السطر النهائي يغيّر البصمة. خزّن نص الجسم الأول مع الحدث في الطرف المرسل إلى أن تُحسم نتيجته.
HMAC يحمي أصالة الطلب وسلامته، ولا يمنع حجب الخدمة على عنوان Apps Script العام. توجد حدود حجم وعدد في الشيفرة لكن لا توجد بوابة حماية شبكية شاملة. حد المعدل وربط الطلب بالجلسة والتحقق من الحقول يجب أن تكون أيضًا لدى المُرسل الخادمي. لا تسمح له بتحويل أي JSON يرسله زائر إلى طلب موقّع دون تحقق.

## 9. الحالات والأحداث: جدول الانتقالات
| الحدث | الحالة السابقة | الحالة الناتجة | الأثر على الرسائل |
| request.create | لا يوجد طلب | SUBMITTED أو INCOMPLETE | استلام، ومتابعة واحدة إذا ناقص وموافق |
| request.complete | INCOMPLETE فقط | SUBMITTED | إلغاء المتابعة والإيصال المعلق القديم، وإنشاء إيصال مناسب |
| request.review | SUBMITTED | UNDER_REVIEW | لا يؤكد وقتًا |
| request.confirm | SUBMITTED أو UNDER_REVIEW أو CHANGE_REQUESTED | CONFIRMED | إلغاء المهام القديمة، وإعداد تأكيد وتذكير صالح |
| request.reschedule | CONFIRMED | CONFIRMED بإصدار موعد جديد | إلغاء رسائل الإصدار القديم |
| request.change_requested | CONFIRMED | CHANGE_REQUESTED | إيقاف التأكيد والتذكير القديمين انتظارًا للاعتماد |
| request.replied | حالة نشطة | دون تغيير الحالة | إيقاف متابعة غير المكتمل |
| request.cancel | أي حالة نشطة | CANCELLED | إيقاف جميع المهام المعلقة |
| request.attended | CONFIRMED | ATTENDED | إيقاف رسائل الموعد، ثم دعوة تقييم إذا وافق |
| request.no_show | CONFIRMED | NO_SHOW | إيقاف جميع المهام المعلقة |
| request.close | غير CLOSED | CLOSED | إيقاف الكل مع سبب RESOLVED أو DUPLICATE أو TEST_ENDED |
| contact.stop | طلب موجود بإصدار مطابق | الحالة نفسها مع stopped | حظر شامل لهذا البريد، وإلغاء المهام عند فحصها |
| request.get | طلب موجود | دون تغيير | قراءة آمنة بلا أسماء أو بريد |
لا يوجد طلب إلغاء من متصفح مجهول بالمرجع وحده. في تجربة الغد، الرد على البريد يصل إلى REPLY_TO، ثم يسجل المسؤول cancel أو change_requested أو stop من القائمة. هذا حل يعمل بنطاق محدود ويجب تسميته تدخلًا بشريًا. لا يُقرأ البريد تلقائيًا ولا تُصنّف الردود بواسطة الذكاء الاصطناعي.
في نمط العرض يسمح المسؤول بتسجيل ATTENDED أو NO_SHOW حتى لو كان الوقت الوهمي في المستقبل، لتوضيح المسار بسرعة. الشيفرة DEMO_ONLY عمدًا؛ هذه ليست قاعدة حضور إنتاجية. الانتقال إلى تشغيل حقيقي يتطلب مصدر حضور وتحققًا زمنيًا معتمدًا.
حالة ATTENDED لا تعني إرسال رسالة أخرى من نوع FOLLOWUP أو REMINDER. لكنها تسمح بمهمة REVIEW جديدة مستقلة وموافق عليها. إن أردت إيقاف كل شيء حتى التقييم، استخدم close أو stop؛ لا تخلط بين استكمال نموذج الطلب وإغلاق دورة الخدمة.

## 10. لماذا هذا التخزين؟ وكيف نمنع التكرار؟
State يحتوي عمود request_id وعمود state_json. داخل JSON توجد الحالة والتفاصيل الدنيا والموافقات والمهام وسجل event_id وبصماته. يجري تحديثها في استدعاء setValues واحد على صف الطلب ثم flush تحت ScriptLock. هذا يقلل فرص حفظ الحدث بلا مهامه أو حفظ الحالة دون ما يثبت تكراره.
هذه طريقة تبسيط لتجربة صغيرة، وليست معاملة ACID أو قاعدة بيانات مضمونة. Google Sheets ليس نظام معاملات متعدد الجداول. إذا نجحت الكتابة ثم فشلت الاستجابة، يعيد المرسل الحدث نفسه؛ يقرأ النظام السجل المحفوظ ويعيد duplicate:true، دون طلب أو رسالة جديدة.
الحظر العام يُكتب في Suppression أولًا عند stop. إذا نجح الحظر وتعطل حفظ الطلب، تُوقف الرسائل احترازيًا رغم بقاء الحالة القديمة حتى إعادة المحاولة. اختير هذا الاتجاه لتقليل خطر مراسلة شخص طلب الإيقاف، لا لإيهامك بأن الجداول تُحدث بمعاملة مشتركة.
القفل واحد للكتابة والإرسال. يجب ألا توجد شيفرة أخرى أو تعديلات يدوية تتجاوز هذا القفل. لو كانت رسالة بدأت الإرسال قبل أن يحصل الإلغاء على القفل، لا يمكن استرجاعها؛ الإلغاء يضمن منع المهام التي لم تبدأ بعد حفظه، لا محو رسالة خرجت بالفعل.
حدود حماية النسخة: 100 طلب، 60 حدثًا محفوظًا لكل طلب، 30 مهمة لكل طلب، 35000 محرف لسجل الحالة، 16000 محرف لظرف النقل و12000 لنص body. هذه حواجز اختبار وضعتها في الشيفرة وليست حصص Google. الأفضل في ليلة العرض 5 إلى 10 طلبات فقط. لا تستخدم هذا التصميم لآلاف السجلات أو كقاعدة بيانات مرضى.
منع التكرار خاص بإعادة الحدث والطلب، وليس منع كل طلبين لهما البريد نفسه. يمكن استخدام بريد اختبار واحد لعدة سيناريوهات. مسؤولية إعادة استخدام request_id لنفس محاولة التسجيل تقع على المُرسل. لا تربط كل طلبات البريد الواحد قسرًا بطلب واحد.

## 11. محرك الرسائل وما تعنيه الحالات فعلًا
| حالة المهمة | المعنى الدقيق | هل تُعاد تلقائيًا؟ |
| PENDING | مهمة لم يبدأ إرسالها بعد | يراجعها المشغّل إن استحقت وكانت مؤهلة |
| SIMULATED | شُغّلت في DRY_RUN وسُجل النص فقط | لا، وتغيير الوضع إلى EMAIL لا يعيدها |
| SENDING | ثُبتت نية الإرسال قبل استدعاء MailApp | لا، يُحوّل المتبقي منها إلى UNKNOWN لاحقًا |
| SENT | أعاد MailApp استجابة نجاح بلا استثناء | لا؛ ليست شهادة تسليم أو قراءة |
| UNKNOWN | استدعاء إرسال غير محسوم أو توقف بعد بدايته | لا، يحتاج مراجعة بشرية |
| CANCELLED | أُلغي بسبب الحالة أو الإيقاف أو انتهاء المهلة | لا |
قد ترى FAILED ضمن فلتر Ops استعدادًا للتوسع، لكنه ليس حالة ينتجها محوّل MailApp الحالي تلقائيًا. لم أختلق DELIVERED أو READ لأن MailApp في هذا التنفيذ لا يعيد معرّف رسالة أو إيصال تسليم موثوقًا.
قبل الإرسال يُفحص: الإيقاف العام، والموافقة، والحظر العام للبريد، وحالة الطلب، وإصدار الموعد، وموعد استحقاق المهمة، وانتهاء صلاحيتها، وعنوان قائمة الاختبار، والحصة البريدية. إلغاء حدث قديم لا يكفي وحده؛ إعادة الفحص لحظة التنفيذ تمنع رسائل متأخرة بعد تغير الحالة.
يُحفظ SENDING أولًا. ثم يستدعى MailApp. ثم يُحفظ SENT إن عاد بنجاح. إذا توقفت العملية بين الإرسال والتحديث تصبح النتيجة مجهولة، وليس «فشلًا يستدعي الإعادة». إعادة المحاولة العمياء هنا قد تُكرر البريد، ولذلك تُمنع تلقائيًا. الثمن المقبول في التجربة هو إحالة الحالة للمسؤول وربما عدم إرسال رسالة، بدل مخاطرة التكرار.
إذا كانت الحصة صفرًا قبل الاستدعاء، تبقى المهمة PENDING مع QUOTA_WAIT ويُعاد فحصها في الدورات التالية إلى انتهاء صلاحيتها. هذا إعادة فحص لما لم يُرسل أصلًا، وليس إعادة محاولة لرسالة مجهولة. لا تُعاد رسائل انتهى موعدها بعد عودة الحصة.
عند UNKNOWN: أوقف السيناريو المعني، وافحص صندوق الاختبار والطابع الزمني والمرجع، وسجل النتيجة خارج الادعاء الآلي. لا تجعل الخلية PENDING يدويًا. لأغراض العرض، أغلق الحالة وأنشئ سيناريو اختبار جديدًا واضحًا بدل إعادة رسالة مجهولة. في الإنتاج يلزم مزوّد بمعرّفات وأحداث تسليم ومنهج مصالحة موثوق.

## 12. الوقت والتسريع والجدولة
الحفظ الداخلي UTC بصيغة ISO، والعرض داخل البريد بتوقيت Asia/Riyadh. لا تستخدم تاريخًا بلا offset. تُضبط المنطقة نفسها في manifest والجدول، ويفحص preflight تطابقهما.
| الإعداد | DEMO_FAST=true | DEMO_FAST=false، وهو لا يزال وضع بيانات وهمية |
| إيصال الاستلام | مستحق فورًا | مستحق فورًا |
| متابعة الناقص | بعد 3 دقائق | بعد ساعة واحدة |
| تأكيد الاستقبال | مستحق فور الاعتماد | مستحق فور الاعتماد |
| تذكير الموعد | بعد 3 دقائق من الاعتماد، بشرط قبل الموعد | قبل الموعد بـ24 ساعة إذا لم يفت وقت التذكير |
| دعوة التقييم | بعد دقيقتين من تسجيل الحضور | بعد 24 ساعة من تسجيل الحضور |
| ساعات التواصل | متجاوزة صراحة لأغراض العرض | من 08:00 حتى قبل 20:00 بتوقيت الرياض |
المشغّل يراجع كل دقيقة، لكن هذا ليس وعدًا بالتنفيذ في الثانية 00. قد تؤخره Google أو الحصص أو طول التنفيذ. «مستحق فورًا» تعني في أول دورة معالجة مناسبة، وليس أن doPost أرسل البريد بنفسه. عند الحاجة يمكنك تشغيل دورة يدويًا من القائمة دون تسريع وقت الاستحقاق.
النسخة تعالج ثلاث مهام كحد أقصى في الدورة، مع ميزانية بدء أعمال قدرها نحو 20 ثانية بين المهام. هذا ليس مهلة صلبة لاستدعاء Google الواحد ولا ضمانًا لزمن التشغيل الكلي؛ خدمة بطيئة قد تستغرق أكثر، وتحديث الجداول خارج هذا القياس. اختبر على حجم صغير ولا تعتمد عليها للضغط العالي.
ساعات التواصل والإعداد الزمني الحالي أمثلة تشغيل اختبار، لا اعتماد لجدول عمل العيادة أو عطلاتها. عند إيقاف DEMO_FAST لا تتحول المنظومة إلى إنتاج. لكل مهمة due_at محسوب وقت إنشائها، وتغيير الإعداد لا يعيد حساب المهام القديمة؛ أنشئ حالات جديدة لاختبار وضع مختلف.

## 13. إنشاء مشروع Google خطوة بخطوة
1. استخدم حساب Google اختبار تملكه، ويفضل حسابًا منفصلًا عن الحسابات المحتوية على بيانات مرضى. فعّل التحقق بخطوتين، ولا تشارك شاشة الأسرار أثناء العرض.
2. أنشئ Google Spreadsheet فارغًا باسم واضح مثل Tabah Dent DEMO. اجعل الوصول Restricted. لا تستخدم Publish to web ولا Anyone with the link لملف الجدول.
3. من داخل الجدول افتح Extensions ثم Apps Script، ليكون المشروع مرتبطًا بالجدول. سمِّ المشروع Tabah Dent External Demo. لا تنشئ نسخة مستقلة بالخطأ، لأن setupDemo يحتاج الجدول المرتبط.
4. أنشئ ملفات Config وDomain وStorage وApi وWorker وAdmin من نوع Script، والصق محتوى ملفات .gs المرفقة دون حذف أو إضافة دوال قديمة. امسح دالة myFunction الافتراضية إن لم تستخدمها. يجب ألا يكون هناك تعريف قديم لـ doPost أو doGet أو runWorker في المشروع.
5. افتح Project Settings وأظهر appsscript.json، ثم ضع محتوى manifest المرفق. runtimeVersion هو V8 وtimeZone هو Asia/Riyadh. لا تضف Gmail read أو Drive أو Calendar، فهي ليست مطلوبة للتجربة الحالية.
6. احفظ المشروع، واختر setupDemo من قائمة الدوال ثم Run. أكمل موافقة Google على حسابك بعدما تراجع الشيفرة والصلاحيات. إذا منعت سياسة المؤسسة النشر أو الصلاحية، لا تتحايل على السياسة؛ عالجها مع مسؤول الحساب أو استخدم حساب اختبار مصرحًا.
7. عُد إلى Google Sheet لتجد State وSuppression وRequests وOutbox وAudit وOps وDashboard. قد يبقى التبويب الافتراضي الفارغ، وهو لا يؤثر في النظام. لا تغيّر أسماء التبويبات المذكورة.
8. افتح Script Properties وأكمل القيم في القسم التالي. setupDemo لا يمسح سجلات قديمة ولا يكتب فوق الأسرار الموجودة، ولا يفعّل البريد أو المشغّل تلقائيًا.
9. شغّل preflight يدويًا. يجب رؤية configuration:PASS. قد تكون worker_triggers_for_current_user:0 الآن، وهذا طبيعي قبل التثبيت. الفحص لا يرسل بريدًا لكنه يفحص الحصة ويتطلب التصريح المناسب.
10. شغّل installWorker مرة واحدة. تكرار تشغيله لا ينشئ مشغّلًا ثانيًا للمستخدم نفسه. افتح Triggers وتحقق من وجود runWorker كل دقيقة فقط. حساب المالك هو الذي ينشئه؛ أدوات Google لا تعرض دائمًا مشغلات المستخدمين الآخرين، لذا لا تنشئه من عدة حسابات.
11. أعد تحميل الجدول لتظهر قائمة Tabah DEMO. افتح Requests وOutbox استعدادًا للتجارب، واترك PAUSED=true وMAIL_MODE=DRY_RUN حتى تكمل أول اختبار استقبال.

## 14. Script Properties: القيم المطلوبة بلا أسرار داخل الأكواد
| المفتاح | القيمة الأولية | الإجراء المطلوب |
| SPREADSHEET_ID | يملؤه setupDemo | يطابق جدول الاختبار المرتبط، وليس رابطًا كاملًا |
| DEMO_MODE | true | لا تغيّره؛ false يوقف هذه النسخة |
| DEMO_FAST | true | تسريع معلن للعرض |
| MAIL_MODE | DRY_RUN | غيّره إلى EMAIL فقط بعد نجاح المحاكاة |
| PAUSED | true | يتحكم في الإرسال، ولا يمنع استقبال الطلبات |
| ALLOWED_EMAILS | فارغ | ضع بريد اختبار حقيقيًا تملكه؛ من 1 إلى 5 مفصولة بفواصل |
| REPLY_TO | فارغ | بريد يراقبه مسؤول التجربة، مطلوب في EMAIL |
| INGEST_SECRET | فارغ | سر عشوائي خادمي مستقل لا يقل عن 43 محرفًا |
| ADMIN_SECRET | فارغ | سر عشوائي آخر، لا يشارك مع استقبال الزوار |
| LAST_WORKER_OK وLAST_WORKER_ERROR | يكتبهما النظام | مؤشرات صيانة، لا دليل تسليم بريد |
ولّد كل سر على جهازك، ولا تستخدم سلاسل i أو a الواردة في الاختبارات. لا تنسخ أسرار الاختبار الثابتة إلى Google. المثال التالي يولد قيمتين مختلفتين؛ احفظهما في مدير أسرار أو مكان آمن، ثم انسخهما إلى الإعدادات وإلى بيئة المُرسل المعني:
```bash
python -c "import secrets; print(secrets.token_urlsafe(48)); print(secrets.token_urlsafe(48))"
```
لا أختار بريدك الشخصي تلقائيًا للإرسال، ولا أرسل رسالة باسمه. أنت تختار العنوان الذي تملكه وتوافق على استخدامه في التجربة. ALLOWED_EMAILS حارس أمان مهم حتى في DRY_RUN؛ لذلك يرفض preflight تركه فارغًا.
هذه النسخة ترسل من حساب Google المنفذ، بالاسم الظاهر Tabah Dent DEMO. REPLY_TO يحدد مكان الرد، ولا يغيّر عنوان المُرسل إلى نطاق العيادة ولا يثبت ملكية علامتها. اختره عنوانًا تراقبه فعلًا؛ MailApp لا يقرأ الردود.

## 15. النشر والاختبار الحي الأول
1. من Deploy اختر New deployment ثم Web app. اجعل Execute as هو حساب المالك. إن كان مسموحًا، اجعل الوصول Anyone لتمكين المُرسل الخادمي من الاتصال دون جلسة Google؛ الحماية التطبيقية تكون بالتوقيع. لا تُغيّر مشاركة Spreadsheet إلى عامة.
2. انسخ Web app URL المنتهي بـ /exec. لا تستخدم /dev، فهو للنطاق التطويري وصلاحيات المحررين. إذا كان Anyone غير متاح في حسابك، فالتكامل المحدد هنا لن يعمل دون متطلب صلاحيات إضافي؛ لا تستبدله بصمت بنشر مختلف وتزعم أنه جُرّب.
3. افتح /exec. يجب أن ترى service:tabah-dent-demo وversion:1.0.0 وLIVENESS_ONLY. لا تفهم ذلك على أنه شهادة جاهزية.
4. جهز متغيرات بيئة جهازك لأداة الاختبار. لا تحفظ الأسرار في مستودع Git، ولا تضعها في أوامر مصورة أو سجل مشترك. استخدم أدوات إدارة الأسرار المعتادة إن كانت متوفرة.
5. ولّد مجلد أمثلة جديدًا بالأمر التالي. استبدل عنوان المثال بعنوانك الموجود في ALLOWED_EMAILS. يُرفض مجلد موجود لحماية أمثلة التجربة السابقة من الاستبدال.
```bash
python tools/make_examples.py --email YOUR_OWN_TEST_EMAIL --out live-examples-01
```
6. اقرأ manifest.json داخل المجلد. يحتوي request_id ومعرّف الحدث ومفتاح الدور لكل ملف. هذه معرّفات وليست أسرارًا، لكنها لا تُستخدم لإعطاء صلاحية عامة للطلب.
7. مثال إعداد متغيرات بيئة في PowerShell، مع الاستبدال محليًا فقط:
```powershell
$env:TABAH_EXEC_URL = "YOUR_REAL_EXEC_URL"
$env:TABAH_INGEST_SECRET = "YOUR_LOCAL_INGEST_SECRET"
$env:TABAH_ADMIN_SECRET = "YOUR_LOCAL_ADMIN_SECRET"
```
وفي macOS أو Linux استخدم export للأسماء نفسها. ملف .env.example مرجع للأسماء فقط؛ أدوات Python لا تقرأ .env تلقائيًا. لا تُثبت مكتبة إضافية ظنًا أنها مطلوبة.
8. تحقق أولًا دون إرسال. استبدل EVENT_ID_FROM_MANIFEST بالقيمة الخاصة بملف 01-create.json:
```bash
python tools/send_event.py --file live-examples-01/01-create.json --event-id EVENT_ID_FROM_MANIFEST
```
9. أرسل الحدث إلى نشر الاختبار، مع بقاء DRY_RUN وPAUSED=true:
```bash
python tools/send_event.py --file live-examples-01/01-create.json --event-id EVENT_ID_FROM_MANIFEST --send --attempts 3
```
10. يلزم ok:true وrequest_id مطابق. من قائمة Tabah DEMO اختر تحديث الجداول. افتح Requests لترى طلبك، ثم Outbox لترى RECEIPT بحالة PENDING. إن كان ok:false فلا تُكمل سيناريو النجاح.
11. أعد الأمر نفسه دون أي تغيير للملف أو المعرف. يلزم duplicate:true ووجود طلب واحد فقط. بهذه الخطوة اختبرت الربط الفعلي ومنع التكرار معًا.
12. من القائمة اختر استئناف بعد التأكيد. ما زال MAIL_MODE=DRY_RUN؛ وافق على تشغيل المعالجة التجريبية ثم شغّل دورة. يجب أن تتحول RECEIPT إلى SIMULATED، وتظهر معاينة النص، دون إرسال حقيقي.
13. لإثبات البريد، أوقف الإرسال من القائمة، وغيّر MAIL_MODE إلى EMAIL، وافحص REPLY_TO وALLOWED_EMAILS ثم preflight. ولّد مجلد أمثلة جديدًا بمعرفات جديدة لأن SIMULATED لا تُعاد. أرسل الإنشاء الجديد، ثم استأنف بعد التأكيد وشغّل دورة واحدة. تحقق من البريد الوارد وSpam والمرجع.
14. عندما يتغير كود Apps Script، احفظه ثم Deploy > Manage deployments > Edit > New version > Deploy لتحديث /exec. الحفظ وحده قد يغيّر ما يشغله محرر المشروع والمشغّل الزمني دون تحديث نسخة Web app المنشورة؛ هذا يسبب تعارضًا خطيرًا إذا لم توحّد النسخة. لا تعدّل ليلة العرض بعد تثبيت النسخة دون إعادة اختبارات القبول.
لا تستخدم curl مع -X POST عند تتبع التحويلات دون فهم سلوكه. أداة Python المرفقة تتبع 302 على طريقة العميل القياسية، وتمنع التحويل إلى مضيف غير متوقع. إذا وصل HTML بدل JSON فهي لا تعلن النجاح، بل تطلب فحص النشر والصلاحيات.

## 16. تشغيل الاستقبال دون تعديل الخلايا
القائمة المرفقة هي واجهة الإدارة البسيطة داخل Google Sheet، وليست تطويرًا للطرف المرئي. افتح Tabah DEMO > تسجيل إجراء استقبال، والصق request_id من عمود Requests، لا المرجع الذي يبدأ TD-. اكتب اسم الإجراء الإنجليزي كما يظهر، ثم الوقت عند طلبه، ثم اعتمد الإجراء في نافذة التأكيد.
لأول سيناريو: أرسل طلبًا، شاهد إيصال الاستلام أو محاكاته، ثم نفّذ review، ثم confirm بوقت مستقبلي، مثل وقت بعد يومين. وقت confirm يجب أن يتقدم عن الوقت الحالي بأكثر من دقيقة وأقل من 90 يومًا. بعد التأكيد شغّل دورة لترى رسالة CONFIRMATION، ثم افتح Outbox لترى REMINDER المعلقة.
لتغيير الموعد نفذ change_requested أولًا إن كنت تمثل رغبة الشخص في التغيير. تُوقف المهام ولا يُعتمد وقت جديد. بعد قرار مسؤول التجربة استخدم confirm بوقت جديد. إذا كان مسؤول التجربة يعتمد إعادة الجدولة مباشرة، استخدم reschedule من حالة CONFIRMED.
عند الرد على البريد، المسؤول يختار replied إذا كان مجرد تواصل يوقف متابعة الطلب الناقص، أو cancel للإلغاء، أو stop لإيقاف التواصل مع البريد كله. replied لا يؤكد موعدًا ولا يلغي تلقائيًا تذكير موعد مؤكد؛ لكل فعل معناه.
المشغّل لا يحلل اللغة ولا يستنتج الحالة من البريد. أخبر الحضور بذلك إن سألوك. هذه ليست فجوة مخفية؛ هي حد واضح يمنع تنفيذ إلغاء أو تأكيد خاطئ بواسطة تفسير آلي قبل اختبار ذلك.
إذا استخدمت ملفات confirm وcancel التي يولدها make_examples.py، فهي تفترض تسلسل create بالإصدار 1 ثم confirm بالإصدار 2 ثم cancel. لا تنفّذ review من القائمة بينهما ثم تستخدم expected_version القديم. اختر مسار القائمة أو الملفات، أو حدّث الإصدار بعد قراءة request.get وبقرار واضح.

## 17. خطة الاختبار الحي: لا تبدأ العرض قبل هذه البوابة
النجاح المحلي وحده لا يكفي. الاختبارات التالية تسجّل في نموذج LIVE_ACCEPTANCE_AR.md المرفق. اكتب «لم يُختبر» عند غياب الدليل، لا «نجح نظريًا». ابدأ بقناة DRY_RUN ثم أعد مسارًا واحدًا فقط بالبريد الحقيقي.
| الاختبار | الإجراء | النتيجة المقبولة |
| النشر | فتح /exec ثم طلب موقّع | JSON صحيح، لا شاشة دخول أو HTML |
| إنشاء | إرسال بيانات وهمية جديدة | ok:true وطلب واحد محفوظ ومرجع مطابق |
| رفض غير صالح | بريد خارج القائمة أو حقل ناقص | ok:false، بلا طلب جديد وبلا بريد |
| تكرار | إعادة الحدث نفسه حرفيًا | duplicate:true وعدد الطلبات لا يزيد |
| صلاحيات | محاولة confirm بمفتاح ingest | FORBIDDEN_EVENT ولا تغيير حالة |
| تسجيل وحفظ | مقارنة الاستجابة وRequests | نفس request_id ونفس الحالة |
| بريد حقيقي | إنشاء جديد وEMAIL ثم دورة | رسالة في صندوقك بمرجع مطابق، وSENT في Outbox |
| تأكيد | اعتماد confirm | CONFIRMED وCONFIRMATION وREMINDER للإصدار الحالي |
| إلغاء قبل الاستحقاق | cancel ثم انتظار أكثر من مهلة التذكير ودورة معالجة | REMINDER ملغاة، ولا بريد تذكير لذلك المرجع |
| استكمال ناقص | INCOMPLETE ثم complete قبل 3 دقائق | لا FOLLOWUP بعد الاستكمال |
| إعادة الجدولة | reschedule | القديمة CANCELLED، وواحدة جديدة للإصدار الجديد |
| إيقاف عام | pauseAll ثم إنشاء مستحق | يُحفظ الطلب ولا تُرسل رسالة |
| إيقاف التواصل | stop ثم محاولة طلب جديد للبريد نفسه | CONTACT_SUPPRESSED ولا إرسال |
| انتهاء الصلاحية | توقيع قديم مع وقت جهاز صحيح | STALE_SIGNATURE |
| المشغّل | تركه يعمل دون ضغط يدوي | يتجدد LAST_WORKER_OK وتُعالج مهمة مستحقة |
| خلو العرض من الأسرار | مراجعة النوافذ والملفات | لا مفاتيح أو بريد خاص غير مطلوب أو بيانات حقيقية |
لا تنفّذ stop على بريد الاختبار الرئيسي في بداية البروفة، لأنه سيمنع كل السيناريوهات التالية لهذا البريد. اجعله آخر اختبار، أو استخدم عنوان اختبار ثانٍ تملكه في القائمة. لا يوجد زر رفع حظر متعجل؛ إعادة التجربة بعده تكون في بيئة اختبار جديدة أو بعنوان اختباري آخر مُصرّح.
اختبارات الفشل المتقدم، مثل توقف العملية بعد إرسال MailApp وقبل الحفظ، نُفذت بمحاكاة محلية متعمدة. لا تُعطّل حساب Google عمدًا لتكرارها قبيل الاجتماع. اختبارات الضغط والتزامن الشبكي الحقيقي واستعادة خدمة Google بعد انقطاعها ليست مثبتة هنا.
معيار GO للعرض الحي: إنشاء حقيقي، وتكرار آمن، وبريد وصل إلى صندوقك، وإلغاء يمنع التذكير، ونشر ثابت، وسيناريو مسجل احتياطي. إذا أخفق أي منها فلا تصف المكوّن غير المثبت بأنه يعمل حيًا. استخدم DRY_RUN مع تصريح بأنه محاكاة، أو التسجيل الحقيقي لما نجح فقط.

## 18. سيناريو العرض لمدة خمس دقائق
1. افتتاح قصير: «هذه تجربة ببيانات وهمية. البريد يعمل على حساب اختبار، ولا يوجد ربط الآن بجدول العيادة أو رقمها. التأكيد هنا يسجله مسؤول التجربة».
2. أرسل طلبًا وهميًا واحدًا من الطرف المرسل الذي جهزه المسؤول عنه. يجب أن يظهر المرجع بعد قبول نقطة الاستقبال، لا قبله. انتقل إلى Requests ثم حدّث الجداول لترى نفس المرجع.
3. اعرض رسالة الاستلام في صندوق الاختبار. إن لم تصل فورًا، اعرض PENDING ولا تزعم التسليم؛ شغّل دورة واحدة إن كانت مستحقة. لا تكرر الإنشاء بمعرف جديد لمجرد تأخر البريد.
4. اعتمد confirm من القائمة بوقت مستقبلي. اعرض حالة CONFIRMED ورسالة التأكيد، ثم صف REMINDER المعلق. قل صراحة إن موعد التذكير مسرّع لثلاث دقائق لأغراض التجربة.
5. ألغِ قبل وصول وقت REMINDER، ثم شغّل دورة وحدّث الجدول. اعرض CANCELLED وسبب الإلغاء. لا تنتظر ثلاث دقائق في صمت؛ انتقل لشرح قاعدة التوقف وارجع بعد الاستحقاق لتثبت عدم خروج تذكير.
6. أعد إرسال حدث الإنشاء نفسه من الطرف المرسل أو أداة الاختبار. يجب أن يعود duplicate:true، وقد تكون الحالة المعادة CANCELLED لأن الاستجابة تُظهر الحالة الحالية، لا الحالة عند الإنشاء الأول. لا تفسّر ذلك بأنه خطأ.
7. افتح Dashboard لعرض ALL_TEST_REQUESTS والحالات، وقل إنها أعداد اختبار وليست مرضى فعليين أو إيرادات. اختم بأن بقية التكاملات تُعتمد بعد معرفة نظام العيادة.
السيناريو الإضافي إن بقي وقت: طلب ناقص بإذن متابعة، ثم complete قبل 3 دقائق. الهدف إثبات عدم إرسال متابعة بعد الاكتمال. لا تفتح دعوة تقييم ومكالمات وإعادة تنشيط في العرض نفسه إذا لم يتسع الوقت.
شريط الزمن لا يضمن أن كل بريد سيصل خلال خمس دقائق بسبب Google والبريد والشبكة. البروفة هي التي تحدد ما يمكن عرضه حيًا، والتسجيل الصادق هو البديل، لا وعد بتوقيت مثالي.

## 20. معالجة الأعطال بلا تخمين
| العرض أو الرمز | الاحتمال الأقرب | التصرف الصحيح |
| HTML بدل JSON أو صفحة دخول | /dev أو صلاحيات نشر أو تحويل إلى login | راجع /exec وExecute as وWho has access |
| CONFIG_* | إعداد ناقص أو غير صالح | راجع Script Properties ثم preflight |
| SETUP_REQUIRED أو USE_BOUND_SCRIPT | مشروع غير مرتبط أو تبويب ناقص | افتح المشروع من الجدول وشغّل setupDemo |
| BAD_SIGNATURE | اختلاف المفتاح أو نص الجسم أو ترميز أو ترتيب رسالة التوقيع | قارن مع أداة Python، ولا تكشف المفتاح في السجل |
| STALE_SIGNATURE | وقت جهاز غير صحيح أو إعادة استخدام توقيع قديم | صحح الساعة وأعد التوقيع فقط |
| IDEMPOTENCY_CONFLICT | نفس event_id مع جسم مختلف أو دور مختلف | احتفظ بالحدث الأصلي، وميّز الحدث الجديد بمعرف جديد |
| REQUEST_EXISTS | إعادة إنشاء لنفس الطلب بمعرف حدث آخر | اقرأ الطلب ولا تنشئ هوية جديدة لإخفاء التعارض |
| VERSION_CONFLICT | إجراء يعتمد إصدارًا قديمًا | اقرأ الحالة، وقرر الإجراء الحالي، ثم حدث جديد |
| INVALID_TRANSITION | إجراء غير متاح من الحالة الحالية | اتبع جدول الانتقالات، لا تغيّر الخلية يدويًا |
| CONTACT_SUPPRESSED | البريد أوقف التواصل عالميًا | لا ترفع الحظر لتجميل العرض؛ استخدم سيناريو اختبار آخر |
| BUSY | دورة أخرى تملك القفل | إعادة محدودة لنفس الحدث، لا حدث جديد |
| INTERNAL_RETRY_SAME_EVENT | فشل غير محسوم أثناء المعالجة | حافظ على المعرفات والجسم واقرأ/أعد المحاولة بأمان |
| QUOTA_WAIT | نفاد الحصة قبل محاولة الإرسال | اعرض الانتظار، ولا تزعم الوصول؛ استخدم المحاكاة المعلنة |
| UNKNOWN | إرسال قد يكون نجح بلا حفظ نتيجته | مراجعة بشرية، دون إعادة آلية |
| CORRUPT_STATE | تعديل يدوي أو بيانات تخزين غير صحيحة | pauseAll، فحص نسخة احتياطية، لا حذف صف لإخفاء المشكلة |
| PENDING لا تتحرك | PAUSED أو غير مستحقة أو quiet hours أو مشغّل غائب | افحص الإعداد والتوقيت وTriggers وExecutions |
| Requests لا تُظهر القبول الأخير | تأخر تحديث نسخ العرض | تحديث الجداول؛ State ونتيجة الحدث هما المرجع |
| SENT ولا بريد في Inbox | قبول من MailApp لا يعني وصولًا | افحص Spam والعنوان والحساب وانتظر؛ لا تكرر تلقائيًا |
| DEMO_RECORD_LIMIT أو EVENT/JOB/STATE_LIMIT | تجاوز حواجز الحجم التجريبي | أوقف التوسع وافتح تجربة صغيرة جديدة، لا ترفعها عشوائيًا |
لو تعطل العرض: أوقف محاولات متتالية غير منضبطة، وقل «حتى لا نستهلك وقت الاجتماع، هذا تسجيل للتجربة نفسها». اعرض تسجيلًا حقيقيًا مع تسميته تسجيلًا. إن لم يوجد تسجيل، اعرض فقط ما نجح: سجل ومحاكاة رسائل، لا شاشة مزيفة تدعي وصول بريد.
الإيقاف العام pauseAll يمنع الإرسال التالي بعد حصوله على القفل، لكنه لا يمحو أحداثًا ولا يوقف استقبال الطلبات ولا يسحب رسالة سبق إرسالها. إذا أردت إيقاف الاستقبال أيضًا أثناء الصيانة، عطّل إرسال الطرف المرسل مؤقتًا أو أوقف النشر وفق إعدادات Google، ولا تفترض أن PAUSED يؤدي الغرضين.

## 21. النسخ الاحتياطي والاستعادة وتثبيت النسخة
قبل البروفة النهائية: شغّل pauseAll، وحدّث الجداول، ثم أنشئ نسخة خاصة من Spreadsheet عبر File > Make a copy، واحفظ ملفات .gs وmanifest والحزمة الحالية في إصدار معلوم على جهازك. النسخ الاحتياطي ليس أتمتة مرفقة؛ هذه خطوة يدوية متعمدة لتقليل الصلاحيات والاعتماديات.
النسخة المنسوخة ليست جاهزة للإرسال تلقائيًا. قد يُنسخ المشروع المرتبط، لكن لا تفترض انتقال Script Properties أو المشغلات أو النشر أو بقاء معرّف الجدول صحيحًا. راجع كل ذلك يدويًا. لا تترك مشغّلين نشطين يرسلان عن نفس بيانات الاختبار في نسختين.
لا تختبر الاستعادة على نسخة الإنتاج أو على طلبات بريدها حقيقي. استخدم مشروعًا/جدولًا معزولًا، واضبط SPREADSHEET_ID للنسخة الجديدة وPAUSED=true وMAIL_MODE=DRY_RUN قبل أي تشغيل. لا تشغّل setupDemo إذا كان SPREADSHEET_ID القديم لا يزال يشير إلى الأصل؛ سيمنع عدم التطابق عمدًا.
استعد State وSuppression معًا، وافحص عدد السجلات وطلبًا معلومًا ثم شغّل تحديث الجداول. الدليل المقبول للاستعادة: الطلب موجود، وحالته ومهامه والحظر مطابقة، ولا بريد خرج. لا تحول مهمة مجهولة إلى pending أثناء الاستعادة.
استعادة نسخة قديمة قد تعيد مهام أُرسلت بعد تاريخ النسخ إلى حالة معلقة. لهذا تبقى نسخة الاستعادة DRY_RUN دائمًا حتى مصالحة الرسائل مع المصدر المتاح. في نسخة MailApp الصغيرة لا يوجد إثبات آلي شامل للتسليم، ولذلك لا أنصح بإعادة تشغيل EMAIL على نسخة قديمة؛ استخدم حالات اختبار جديدة بعد إغلاق القديمة.
بعد تثبيت النسخة: سجّل deployment version ووقت النشر ونتيجة آخر preflight، واحتفظ بـ SHA256SUMS.txt المرفق للتحقق من ملفات التسليم. لا تغيّر عقد v1 أو الحالات أو الصلاحيات في منتصف البروفة دون إعادة فحص الطرفين.

## 22. خريطة النقل إلى WhatsApp والأنظمة الأخرى
المستقر عند الانتقال: request_id وevent_id وحالات الطلب وexpected_version وقواعد الإلغاء والأهلية وسجل المهام. المتغير: contact وقناة الموافقة وقوالب الرسائل ومحوّل الإرسال وأحداث المزوّد. التنفيذ الحالي يجمع email فقط، لذلك توجد هجرة بيانات مطلوبة قبل WhatsApp، وليست موجودة في الطلبات القديمة تلقائيًا.
| مرحلة التوسع | التغيير المطلوب | ما لا يجوز افتراضه |
| عنوان التواصل | إضافة قناة وphone_e164 والتحقق منه | البريد لا يعطيك رقم WhatsApp |
| الموافقات | حفظ إذن خاص بالمنشأة والقناة والغرض ونصه ووقته | موافقة البريد ليست موافقة WhatsApp تلقائيًا |
| محوّل الإرسال | إضافة sendWhatsAppAdapter بدل توصيل منطق الحالات بالمزوّد | لا يستبدل sendEmailAdapter بمجرد إعادة تسمية |
| القوالب | أسماء معتمدة ولغات ومتغيرات وتحقق من الغرض | كل رسالة خدمية أو مجانية تلقائيًا |
| الإرسال | حفظ provider_message_id والنتيجة الموثقة | قبول الطلب لدى المزوّد ليس قراءة |
| أحداث التسليم والردود | بوابة تتحقق من توقيع webhook ثم تطبع أحداثًا موثوقة | لا نثق بـstatus يرسله عميل مجهول |
| منع الازدواج | قناة نشطة محددة للحدث، أو fallback بقواعد مكتوبة | لا إرسال Email وWhatsApp معًا بلا إذن |
| تجربة الانتقال | رقم اختبار رسمي وأحداث متكررة ومتأخرة وتوقيع غير صالح | نجاح Email يثبت WhatsApp |
وثائق Meta تؤكد متطلبات الإذن والقوالب للرسائل التي تبدأها المنشأة. يجب مراجعة سياسة نافذة الخدمة والتصنيفات والأسعار الحالية عند التفعيل؛ هذا التقرير لا يثبت تعرفة سعودية ولا يعيد تأكيد أي تاريخ تسعير مستقبلي في التقرير السابق.
لأن Apps Script في doPost المستخدم هنا لا يقدّم واجهة موثقة لقراءة رؤوس HTTP الاعتباطية، فإن تكامل webhook الذي يحتاج التحقق من توقيع في header يُنفذ عبر بوابة خادمية مناسبة تحت تحكمك، لا تعطيل فحص التوقيع. تمرر البوابة أحداثًا موقّعة داخليًا بعد التحقق الأصلي. هذه إضافة إنتاجية لاحقة لا حاجة لها للبريد التجريبي.
Google Calendar ليس ضروريًا هنا. إضافته الآن قد تجعل حدثًا في تقويم اختبار يبدو كأنه موعد متاح بالعيادة، وهو غير صحيح. إن طلب لاحقًا، استعمل تقويم اختبار منفصلًا، واحفظ calendar_event_id، ونفّذ مزامنة إنشاء/تحديث/إلغاء بإصدارات متطابقة، وحدد المصدر المعتمد والتعارضات قبل الوعد. لا تُنشأ أحداث Calendar بواسطة الحزمة الحالية.
برنامج العيادة: احصل أولًا على اسمه وإصداره ووثائق API ونظام الصلاحيات ومصدر الحضور والمواعيد. ثم ضع محوّلًا للطلب/التأكيد/الإلغاء مع خارطة حالات ومعرف خارجي واختبارات رفض وفشل واستعادة. لا توجد شيفرة صحيحة لتكامل مجهول؛ أي كود «عام كامل» له سيكون ادعاءً غير موثوق.
المكالمات الفائتة تحتاج حدثًا من السنترال أو المزوّد، لا عدّادًا متخيّلًا. إعادة التنشيط تحتاج بيانات قابلة للاستخدام وأساس تواصل ومعيارًا يعتمدُه الفريق، لا حملة آلية لكل مَن غاب. الوكيل الصوتي والتشخيص وإيراد منسوب مستثناة من عرض الغد كما نص التقرير المرجعي.
طلب التقييم الإنتاجي يكون بعد حضور حقيقي وبمعيار محايد، مع رابط Google الذي تزوده العيادة وقناة شكوى موازية للجميع. لا يوجد مسار «الراضون فقط إلى Google»، ولا خصم مقابل تقييم. لا تنشر تقييمًا حقيقيًا من التجربة الوهمية.

## 23. ضوابط بيانات وأمان قبل أي إنتاج
هذه الحزمة متعمدة القصر على بيانات وهمية. ليست شهادة امتثال ولا نظامًا صحيًا ولا وسيلة لمعالجة سجلات المرضى. موعد مرتبط بشخص ومنشأة صحية قد يحمل حساسية، حتى دون تشخيص مكتوب. قبل الإنتاج تعتمد العيادة تدفق البيانات والصلاحيات والاحتفاظ ومواقع المعالجة والمزودين والمتطلبات النظامية.
لا تجعل ملف Sheet عامًا، ولا تسمح للمستلمين بالوصول إليه. يشاهد الحضور شاشة تعرض سجلات وهمية فقط. لا تُظهر Script Properties أو متغيرات البيئة أو سجل بريدك الشخصي. تجزئة البريد في Suppression ليست تشفيرًا يمنع التخمين، فلا تعامل الجدول كبيانات مجهولة يمكن نشرها.
لا ترفع أسرار التكامل أو بيانات حقيقية إلى الذكاء الاصطناعي داخل المحرر. زوّده بأسماء متغيرات البيئة والعقد والأمثلة الوهمية فقط. أوقف أي تسجيل تلقائي للجسم الكامل في جهة المُرسل أو خدمات التحليلات. سجلات API الحالية تطبع رموز خطأ لا محتوى الطلب.
النسخة لا توفر عزل فروع أو مستخدمين أو rate limiting موزعًا أو نسخًا احتياطيًا آليًا أو تدقيقًا غير قابل للتلاعب. Audit يمكن لمالك الملف تعديله، وState ليس سجلًا تنظيميًا محصنًا. هذه متطلبات إنتاج مستقلة.
إرسال Email عبر MailApp في حسابات المستهلك له حد منشور 100 مستلم يوميًا، وGoogle Workspace له حدود أعلى وفق نوع الحساب. توثيق Google يذكر أيضًا حدًا عامًا قدره 6 دقائق للتنفيذ وحصص وقت للمشغلات. قد تتغير القيم وتنطبق حدود إضافية؛ النظام يفحص getRemainingDailyQuota بدل افتراض أن كامل الحصة متاح.
لا تستخدم معظم الحصة في بروفة متكررة. اختبر القواعد بـDRY_RUN ثم أرسل عددًا محدودًا من الرسائل الحقيقية. تذكّر أن إنشاء وتأكيد وتذكير وتقييم قد تنتج عدة رسائل لطلب واحد، فلا تساوِ عدد الطلبات بعدد المستلمين اليوميين.

## 25. القرار الأخير قبل العرض
لا تضف منصة جديدة الليلة إذا ثبت الحفظ والبريد والإلغاء. أثبت المسار ثم ثبّت النسخة وسجّلها. قيمة التجربة أن ترى مرجعًا واحدًا ينتقل بحالة صحيحة، وأن يوقف الإلغاء مهمة فعلية، لا أن تملك أكبر عدد من الأدوات.
سلّم HANDOFF_VSCODE_AR.md كاملًا للذكاء داخل المحرر مع الحزمة. اطلب منه تأكيد فهم عقد v1 والحدود قبل التعديل، ثم تنفيذ اختبار ربط واحد ومراجعته بالمعرف، دون تعديل محرك Apps Script أو اختراع وظائف خارجية إضافية.
اعرض فقط ما تشهد عليه الأدلة: الشيفرة خضعت لاختبارات محلية، والربط الحي يثبت حين تختبره أنت، ووصول البريد يثبت في صندوقك، والموعد الحقيقي لا يثبت إلا من المصدر المسؤول بالعيادة. بهذا تحمي العرض من الخطأ ومن المبالغة في الوقت نفسه.

## ملحق ج. دليل الاختبارات
اختبارات Node موجودة كاملة في tests/run-tests.cjs، ونتائج التشغيل الفعلية في tests/results.json. لتكرارها دون اتصال بخدمات Google:

```bash
node tests/run-tests.cjs
```
